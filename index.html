How the Issues page works

The Issues page lists only problems dumbdock can prove from the Docker daemon and the Traefik API. It never guesses from log text, and an empty page means nothing was found in the sources it could check — not that nothing is wrong.

Severity

  • error — a broken or unsafe state that needs attention, such as an unhealthy container, an unreachable proxy, a DOWN backend, or database data that will be lost when its container is recreated.
  • warning — a deviation worth knowing about that does not by itself break anything, such as a publicly bound port or an available image update.

Grouping, counts, and refresh

One row is one finding. Rows are grouped by issue type, and the number beside the Issues navigation button is the count of active, unacknowledged rows. The page is a cache read: dumbdock collects findings in its own background poll every 10 seconds after you sign in, so opening the tab does not itself query Docker or Traefik.

Explaining a row

The small info control beside each row's title explains that issue type. Hover it, focus it with the keyboard, or tap it to open a short description and a Read the full explanation link; click it to pin the popover, press Escape to close it, and click anywhere else to dismiss it. The popover describes the type, not the specific container in the row — this page is the full reference for every type.

Acknowledging

Acknowledge moves a finding to the Acknowledged table without hiding that it exists: it leaves the badge count and the active list, and it survives a restart. dumbdock keeps an acknowledgement until a complete collection confirms the finding is gone; if a source could not be checked, the acknowledgement is retained rather than silently cleared. Unacknowledge puts it back.

Coverage

When a source cannot be checked — the Docker health query failed, a Traefik endpoint errored, or the Traefik API is disabled for this run — the page says Collection: partial and lists the reason. A partial collection never counts as healthy, and acknowledgements are not pruned while it lasts. A disabled Traefik gate is shown as exactly one Traefik API unavailable (disabled until restart) row, because restarting dumbdock is the only way to retry it.

Container health

error Docker's own healthcheck says the container is failing.

What it means

Docker reports health=unhealthy for a container that is running but not passing the healthcheck its image or compose file defines. The process may still be up; what failed is the test that proves it works.

Why it appears

dumbdock reads the daemon's health filter — it never infers health from the status text. Only containers the dashboard currently shows are considered, and containers you denylisted are skipped. A container that is stopped, paused, or restarting is not a health finding.

How to resolve it

  • docker inspect --format '{{json .State.Health}}' <container> shows the failing test and the last few probe outputs.
  • docker logs --tail 100 <container> usually shows what the probe is hitting.
  • Fix the service, or fix the check when the check is wrong (an HTTP path that needs auth, a port that moved, a start period that is too short).
  • Recreating the container with a corrected healthcheck is what clears the row; dumbdock does not restart or repair anything.

Exempt and out of scope

A container with no healthcheck, or one whose health is starting, is not a finding. Raw logs are never read into an issue row.

Traefik API

error warning dumbdock cannot read Traefik's read-only API.

What it means

An error means every Traefik endpoint failed, or the boot attempt gate gave up and disabled API work for this run. A warning means one endpoint returned an error while the rest answered, so part of the Traefik page is stale.

Why it appears

Traefik does not expose its API by default. dumbdock resolves the API URL from the dumbdock.traefik.api label, then TRAEFIK_API_URL, then the container's network IP, then a published port. After three failed attempts at startup it disables API collection until dumbdock restarts, and reports that as one terminal row even if the Traefik container has since disappeared.

How to resolve it

Enable the API (--api.insecure=true on a private network, or the api@internal router), point dumbdock at it explicitly, and add credentials when it is protected. The step-by-step guide, including the verification curl, is under Configure Traefik API Access. If the row says disabled until restart, restart dumbdock after fixing the API — the gate re-arms on every start.

Exempt and out of scope

No Traefik container at all is not a finding. A 404 from an endpoint dumbdock knows is optional (for example TLS certificates when none are configured) is not configured, not an error, and partial endpoint warnings keep the rows other endpoints produced.

Traefik backends

error A server behind a Traefik service is DOWN.

What it means

A Traefik HTTP or TCP service lists a load-balancer server whose status is DOWN. Requests routed to that service can fail or be sent to a healthy sibling with a delay.

Why it appears

dumbdock reads each service's per-server status from the API. The row names the service and the exact server URL, so a stale target — an old container IP, a port nothing listens on, a container that was replaced — is identifiable without opening Traefik's own dashboard.

How to resolve it

  • Confirm the target container is running and on the same Docker network as Traefik.
  • Check the port the service points at, for example traefik.http.services.<name>.loadbalancer.server.port.
  • Look for a stale file-provider entry that still names a removed container.
  • The Traefik tab lists the service and its servers; it clears once Traefik reports the server UP.

Exempt and out of scope

Only an explicit DOWN is a finding. A server reporting UP, or a service with no server status, produces no row.

Traefik entities

error warning A router, service, or middleware is not healthy.

What it means

Traefik labels an HTTP or TCP router, an HTTP or TCP service, or a middleware as error (reported here as an error) or as disabled or warning (reported as a warning). The row names the kind and the entity.

Why it appears

dumbdock copies the status Traefik itself reports. It never invents an entity that Traefik does not list, so this is always Traefik's own verdict on a configuration it loaded.

How to resolve it

  • Open the Traefik tab and find the entity by name; the status column matches this row.
  • For error, check the router rule, the referenced service or middleware name, and the provider it comes from (Docker labels or a file provider).
  • For disabled, confirm whether that is deliberate — for example a router switched off with traefik.enable=false.
  • Traefik's own log explains the specific parse or reference failure.

Exempt and out of scope

Entities that are enabled or carry an unknown status are not findings, and dumbdock never fabricates a missing entity.

Database backups

error warning A detected database has no recent backup evidence.

What it means

An error means the dataset is required to have a backup, an evidence provider is configured, and nothing was found. A warning means a dump exists but is older than the dataset's policy.

Why it appears

The Storage scanner detects a database engine (MariaDB, MySQL, PostgreSQL, or SQLite) in a compose-managed service, reads its policy, and checks the dataset's backups/ directory for a dump artifact. Evidence is freshness metadata: the newest file name and timestamp, not the dump's contents.

How to resolve it

  • Run the reference job (scripts/backup-databases.sh) or your own dump, writing the artifact into the dataset's backups/ directory under the data root.
  • Push freshness metadata from outside the container with POST /api/backups/report and DUMBDOCK_BACKUP_TOKEN when a job runs elsewhere.
  • Adjust the policy per service if the current one is wrong for that data.
  • The Storage tab shows the dataset, the last artifact, and the policy it was judged against.

Exempt and out of scope

dumbdock.backup.disabled=true makes the dataset exempt — visible, never a finding. A dataset whose evidence provider is not configured is unverified and counts as coverage, not a finding. A failed push report is not evidence of a backup, and dumbdock does not verify a dump's contents (use pg_restore --list, gzip -t, or sqlite3 "pragma integrity_check;" for that).

Storage paths

error warning Files or data sit outside the storage layout.

What it means

A error is database data stored in the container's own filesystem, which is lost when the container is recreated. A warning covers a compose file outside the container root, application or database data stored beside the compose file, data in a named or anonymous Docker volume, and data outside the data root.

Why it appears

dumbdock compares each compose-managed container's mounts and detected database directories against the documented layout: compose files under /opt/containers/<project>/ and persistent data under /srv/containers/<project>/<service>/. Roots come from DUMBDOCK_CONTAINER_ROOT and DUMBDOCK_DATA_ROOT, then the config file, then those defaults.

How to resolve it

  • Move the compose file into the container root and recreate the project from there.
  • Bind-mount the service's data from its /srv/containers/<project>/<service>/ directory instead of using a Docker volume.
  • Move a database directory out of the application checkout into that data directory, then restart the service.
  • A bind mount of an application checkout can be waived with dumbdock.storage.ignore when it is genuinely source, not data.
  • The Storage tab shows each mount, its classification, and the expected path.

Exempt and out of scope

Only compose-managed containers are evaluated; a standalone docker run container is out of scope. A configured root that is not mounted into the dumbdock container is reported as not-mounted coverage, never as a finding, and a dataset row suppresses the duplicate volume-mount row for the same destination.

Exposed ports

warning A published port is reachable from more than localhost.

What it means

A published port is bound to every interface (0.0.0.0 or ::) or to a public IP, so anything that can reach the host can attempt a connection. The row lists the addresses it found.

Why it appears

dumbdock classifies every published port binding it sees. This is a warning, not an error: publishing a web port is often exactly what you meant, so the row is a reminder to confirm it.

How to resolve it

  • Bind to localhost when only the host needs it: -p 127.0.0.1:8080:8080, or the same address in a compose ports entry.
  • Bind to a private address when the service is for an internal network only.
  • Front a port that must be public with a reverse proxy that terminates TLS and enforces auth.

Exempt and out of scope

Bindings on 127.0.0.1, ::1, and private addresses are not findings. An EXPOSE line that publishes nothing is not a finding either.

Image updates

warning A newer image digest exists for the running tag.

What it means

The registry reports a newer digest for the image tag the container is running. The container keeps running the image it started with until it is pulled and recreated.

Why it appears

dumbdock's background checker asks Docker Hub and GHCR anonymously for the tag's current digest, caches the answer for six hours, and compares it with the running container. It sends no credentials and never pulls an image.

How to resolve it

  • Read the release notes for the image, then pull and recreate the service when it suits you: docker compose pull <service> && docker compose up -d <service>.
  • Acknowledge the row if you are deliberately holding the current version.
  • Turn the check off with DUMBDOCK_UPDATE_CHECK=false when outbound registry access is unwanted.

Exempt and out of scope

An update state of unknown or error — an unsupported registry, a local-only image, or a failed lookup — is not a finding. Denylisted containers are skipped, and dumbdock never changes an image or restarts a container.

Docker Engine

warning The daemon is older than the latest stable Moby release.

What it means

The Docker daemon reports a version older than the newest stable moby/moby GitHub release. This is advisory: distribution packages deliberately lag upstream, and a host that is working does not need an immediate upgrade.

Why it appears

dumbdock caches the latest release for 24 hours (retrying after 15 minutes on failure), compares it with the daemon's version, and keeps the last good comparison when a later fetch fails. It never upgrades anything.

How to resolve it

  • Confirm the version with docker version.
  • Upgrade through your distribution (for example apt or dnf) or Docker's own packages, planning for a daemon restart.
  • Check the release notes for breaking changes before a major jump.

Exempt and out of scope

When the comparison is unavailable — the release feed failed or either version cannot be parsed — the page reports coverage instead of a row, because an unavailable check is not evidence of an old daemon.

Traefik version

warning The detected Traefik major version is not 3.

What it means

dumbdock requires Traefik v3. A v2 (or unparseable) version means parts of the Traefik tab may be missing or rendered differently. The row is informational; it never blocks the rest of the dashboard.

Why it appears

dumbdock reads the major version from Traefik's /api/version. The Traefik tab shows the same condition as a banner, the server logs it once per state change, and this row makes it visible from the Issues page.

How to resolve it

  • Upgrade Traefik to v3, following Traefik's migration notes for entrypoints, providers, and the API.
  • Reload the Traefik tab afterwards; the row clears on the next poll once v3 answers.

Exempt and out of scope

A missing Traefik container, or a version that cannot be parsed, is reported as information rather than as a Traefik API failure. This row does not imply any entity or backend finding.

Integration API

error dumbdock cannot read an integration's own API.

What it means

An integration that dumbdock detected answered nothing, rejected its credentials, or was disabled by its boot attempt gate. This is about the integration's API — Watchtower's HTTP API or PruneMate's status endpoint — not about Traefik, which keeps its own four categories.

Why it appears

Each integration polls its API on the same 10-second cycle, read-only. After three failed attempts at startup, that integration's gate disables its work for the rest of the run and reports one stable row even if the container has since disappeared. Other integrations are unaffected: a disabled Watchtower never disables PruneMate.

How to resolve it

  • Confirm the endpoint is enabled. Watchtower serves it only with --http-api-metrics; see Enable the Watchtower HTTP API.
  • Point dumbdock at it through the override layers — integrations.<id>.url in the config file, the dumbdock.integration.<id>.url container label, or DUMBDOCK_INTEGRATION_<ID>_URL; see Override integration detection.
  • Send the token in the matching token field; it travels in a header only and is never logged.
  • If the row says disabled until restart, restart dumbdock after fixing the endpoint — the gate re-arms on every start.

Exempt and out of scope

An integration that is not detected and not forced is not a finding. When Watchtower is running without the metrics endpoint, the page reports coverage instead of this error. dumbdock never calls an integration's mutating endpoints: no Watchtower update, no PruneMate run.

Integration status

warning The integration reports a problem with its own work.

What it means

The integration is reachable but reports something wrong: Watchtower counted one or more failed container updates in its last scan, or PruneMate has never completed a prune, or its last completed prune is older than the stale threshold.

Why it appears

dumbdock reads the vendor's own counters and timestamps and never infers a failure. The row names the integration, and the Integrations tab shows the same counts, the last run time, and the threshold it was judged against.

How to resolve it

  • For failed updates, read Watchtower's log for the container it could not update, then fix that image or its permissions.
  • For a prune that never ran or is stale, check PruneMate's schedule in its own UI and confirm the container has been running long enough to have completed one run.
  • Acknowledge the row while the cause is deliberate, such as a paused pruning schedule.

Exempt and out of scope

An integration with no API configured produces a coverage warning, not a finding, and nothing is inferred when a metric is absent. dumbdock never triggers an update or a prune to "fix" the row.

Configure Traefik API Access

The dumbdock Traefik tab reads Traefik's read-only API to show routers, services, middlewares, entrypoints, and TLS certificates. Traefik does not expose this API by default, so dumbdock may log connection refused errors until it is enabled. This guide covers both ways to enable it, how to verify it works, and how to troubleshoot failures.

ℹ
Which option should I use?
Use Option 1 (insecure API) only when Traefik is reachable on a trusted network (for example, a private Docker network or localhost). Use Option 2 (secured API) when Traefik's dashboard/API could be exposed beyond your host — it requires auth and is the recommended choice for anything public.

How dumbdock finds the API

dumbdock resolves the Traefik API URL with this fallback chain:

  1. The dumbdock.traefik.api label on the Traefik container (used as-is).
  2. The TRAEFIK_API_URL environment variable set on the dumbdock container.
  3. The Traefik container's Docker network IP with port 8080 (or the port from --entrypoints.traefik.address=:PORT).
  4. The first published TCP port on 127.0.0.1 (preferring 8080).

If every endpoint fails at the resolved URL, dumbdock probes fallbacks in order — the published 8080/tcp port, the container IP on 8081, then any other published TCP port — and uses the first one that answers /api/version.

Option 1 — Insecure API (quick start)

Start Traefik with --api.insecure=true. This serves the dashboard and API on the traefik entrypoint (default port 8080).

docker run -d --name traefik \ -p 80:80 -p 8080:8080 \ -v /var/run/docker.sock:/var/run/docker.sock \ traefik:v3 --api.insecure=true --providers.docker

Compose equivalent:

services: traefik: image: traefik:v3 command: - --api.insecure=true - --providers.docker=true ports: - "80:80" - "8080:8080" volumes: - /var/run/docker.sock:/var/run/docker.sock

Security note: --api.insecure=true has no authentication. Keep port 8080 on a private network (do not publish it to a public interface) and let dumbdock reach it over the Docker network.

No port publishing needed: you do not have to expose 8080 to the host. If dumbdock shares a Docker network with Traefik, it reaches the API directly at the Traefik container's IP on port 8080 — omit the -p 8080:8080 line (or the 8080:8080 entry under ports) entirely:

docker run -d --name traefik \ -p 80:80 \ -v /var/run/docker.sock:/var/run/docker.sock \ traefik:v3 --api.insecure=true --providers.docker

With the port unpublished, 8080 is only reachable from inside the Docker network the Traefik container is attached to. Make sure the dumbdock container is on that same network (for example, join both to a shared user-defined network such as traefik).

Test the API from the Traefik container

To confirm the API is listening inside the network without publishing the port, run a request from a shell in the Traefik container itself:

# Traefik v3 (and v2.6+) ships no curl; use wget if curl is missing docker exec traefik wget -qO- http://127.0.0.1:8080/api/version

If curl is available in your image, the equivalent is:

docker exec traefik curl -s http://127.0.0.1:8080/api/version

To test reachability across the network (the way dumbdock connects), run the request from the dumbdock container using the Traefik container's name instead of 127.0.0.1:

docker exec dumbdock wget -qO- http://traefik:8080/api/version

A successful response is the same version JSON shown under Verify it works. If wget/curl is not present in the image, install it in a throwaway container on the same network:

docker run --rm --network traefik curlimages/curl -s http://traefik:8080/api/version

Option 2 — Secured API (recommended for public exposure)

Expose the api@internal service through a router instead of the insecure entrypoint, optionally protecting it with auth middleware. Example dynamic configuration (Docker provider labels on the Traefik container):

labels: - "traefik.enable=true" - "traefik.http.routers.api.rule=Host(`traefik.example.com`)" - "traefik.http.routers.api.entrypoints=websecure" - "traefik.http.routers.api.tls=true" - "traefik.http.routers.api.service=api@internal" - "traefik.http.routers.api.middlewares=api-auth" # Basic auth (use `htpasswd -nb user pass` to generate the value) - "traefik.http.middlewares.api-auth.basicauth.users=admin:$apr1$..."

Then point dumbdock at it explicitly with the TRAEFIK_API_URL environment variable (this overrides auto-discovery):

environment: - TRAEFIK_API_URL=https://traefik.example.com

Alternatively, label the Traefik container itself with dumbdock.traefik.api and dumbdock will use that URL as-is.

Authentication for a secured API

If Traefik's API is protected, give dumbdock credentials (sent server-side only — they never reach the browser):

  • Bearer token: set TRAEFIK_API_TOKEN on the dumbdock container, or traefikAPIToken in dumbdock.json.
  • Basic auth: set TRAEFIK_API_USER and TRAEFIK_API_PASS on the dumbdock container.

Verify it works

From the machine running dumbdock (use the same host/port dumbdock will use):

curl -s http://:8080/api/version

A working API returns JSON like:

{"Version":"3.x.x","Codename":"...","StartDate":"...","Goversion":"go1.x"}

If you configured auth, add it to the request:

# Bearer curl -s -H "Authorization: Bearer " http://:8080/api/version # Basic curl -s -u user:pass http://:8080/api/version

Then open the dumbdock Traefik tab — it should show the Traefik version, overview stats, and router/service tables.

Troubleshooting

  • "Traefik container detected but API is not accessible" — the API host/port dumbdock resolved is not answering. Confirm --api.insecure=true or the api@internal router is enabled, and that the port is reachable from the dumbdock container.
  • Logs show connection refused on every endpoint — nothing is listening on the resolved URL, usually because the API is not enabled or is on a different port. dumbdock logs this once per state change and logs traefik: API recovered when it comes back.
  • Wrong URL chosen — set TRAEFIK_API_URL (or the dumbdock.traefik.api label) to bypass auto-discovery entirely.
  • 401/403 responses — the API is up but requires auth. Set TRAEFIK_API_TOKEN or TRAEFIK_API_USER/TRAEFIK_API_PASS.
  • Partial data — a few endpoints may 404 when a feature is unused (for example, no TLS certificates configured). This is normal; the tab shows a partial-data notice.
  • "Unsupported Traefik version" — dumbdock requires Traefik v3. The Traefik tab shows this banner (and the server logs it once) when the detected major version is not 3. Upgrade Traefik to v3, then reload the tab.

Enable the Watchtower HTTP API

dumbdock reads Watchtower's metrics endpoint to show scan counters, last-scan results, and how many containers it monitors. It never calls the update endpoint, so a dashboard visit cannot trigger an image update.

What to enable

  • Metrics API — start Watchtower with --http-api-metrics (or WATCHTOWER_HTTP_API_METRICS=true) and an API token in WATCHTOWER_HTTP_API_TOKEN. dumbdock sends the token as a bearer header.
  • Port — Watchtower serves the API on port 8080 inside its container. dumbdock tries the container network address first, then a published host port.
  • Update API only — --http-api-update without metrics lets Watchtower accept triggers, but exposes nothing dumbdock can read. The card shows a note asking for metrics.

Verify it works

From the dumbdock container (or any host that can reach Watchtower):

curl -s -H "Authorization: Bearer $TOKEN" http://watchtower:8080/v1/metrics

Expected: Prometheus text with watchtower_containers_scanned, watchtower_scans_total, and related counters. The Integrations card then shows those figures.

Caveats

  • The metrics API is experimental in Watchtower and reports counters since its process started; there is no last-scan timestamp to display.
  • Monitored containers are counted from the com.centurylinklabs.watchtower.enable=true label. Without label filtering the card reports "all running" instead of a precise figure.
  • A wrong or missing token appears as 401 in the card and one integration-api finding in Issues.

Override integration detection

dumbdock detects Traefik, Watchtower, and PruneMate by their image repository. When that is wrong — a custom-built image, a renamed fork, two instances, or a tool you do not want monitored — override the detection instead of changing the image.

Three ways to set an override

They are consulted in this order, so a config block beats a label and a label beats an environment variable:

  • Config file — an integrations block in dumbdock.json: "integrations": {"watchtower": {"enabled": true, "url": "http://watchtower:8080", "token": "..."}}.
  • Container label — dumbdock.integration.watchtower.enabled, .url, .container, .token, .user, .pass.
  • Environment — DUMBDOCK_INTEGRATION_WATCHTOWER_ENABLED, _URL, _CONTAINER, _TOKEN, _USER, _PASS. The id is upper-cased, so DUMBDOCK_INTEGRATION_PRUNEMATE_URL.

What each field does

  • enabled — false hides the integration completely: no polling, no findings, and a "Hidden by configuration" card. Use it when a matching container must not be monitored.
  • container — pins one container by name and treats it as this integration even when its image does not match. This covers a custom build and a host with two instances. A pin that matches nothing reports "Not detected"; it never falls back to another container.
  • url — polls the API at that address with no container needed. Use it for a tool on another host or behind a proxy. Only http/https is accepted, credentials in the URL are rejected (use token or user/pass), and link-local addresses are refused.
  • token / user / pass — credentials for the API. They are sent in the authorization header and never appear in logs, payloads, or Issues.

Examples

labels:
  - "dumbdock.integration.watchtower.container=my-watchtower"
  - "dumbdock.integration.prunemate.enabled=false"

Traefik keeps its original names as aliases: dumbdock.traefik.api, TRAEFIK_API_URL, TRAEFIK_API_TOKEN, TRAEFIK_API_USER, and TRAEFIK_API_PASS still work.
